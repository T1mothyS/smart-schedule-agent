# 日历里的事项：人话版说明

- Status: LIVING
- Scope: 创建、编辑、AI 确认、周期事务及兼容字段；不迁移历史数据。
- Last verified: 2026-09-19；`c35f4c5` 数据实现。
- Authority: `schedule-input.ts`、`schedule-time.ts`、`schedule-store.ts`、`reminder-input.ts`、`reminder-store.ts` 及实际表单。
- Update trigger: 创建规则、字段含义、周期计算或导入规则变化。
- Do not use for: 推断手机提醒、双向同步或生产状态。

## 到底有几种？

按用途是 **3 大类：日程、待办、周期事务**。按平时填写的方式，可以理解成 **6 种常见形态**：

| 形态 | 例子 | 你要表达的意思 |
|---|---|---|
| 定时日程 | 今天 15:00～16:00 开会 | 一段要安排出来的时间；结束时间可选 |
| 全天日程 | 明天休假 | 占某一天，不强调几点钟 |
| 定时待办 | 明天 14:00 拿快递 | 一个要做完的动作，指定几点；不保存持续时长 |
| 全天待办 | 明天拿快递，几点都行 | 确定要在哪天做，不指定几点 |
| 无固定期限待办 | 有空整理资料 | 没定哪天，留在挂起待办里，直到处理 |
| 周期事务 | 每月还信用卡 | 保存长期规则，再分别记录每一期是否完成 |

底层普通事项只有 `event`（日程）和 `todo`（待办）两种类型，全天、无固定期限、重复都是附加属性。周期事务使用另一套“规则＋每一期”记录。手动新建、AI 确认、邮件/智能导入是创建入口，不应再各算一种数据类型；AI 草稿需要确认才成为正式事项。

## 普通日程和待办保存什么？

| 信息 | 是否需要你填写 | 系统里的字段 | 通俗解释 |
|---|---|---|---|
| 标题 | 必填 | `title` | 做什么；不能空白，最多 200 字符 |
| 类型 | 有默认值，可选 | `type` | 日程还是待办 |
| 所属日历 | 有默认值，可选 | `calendar_id` | 放在哪本日历，默认个人日历，必须属于当前账号 |
| 日期/开始时间 | 有日期事项必填 | `start_time` | 定时事项写日期和时间；全天写日期或当天零点 |
| 结束时间 | 日程选填 | `end_time` | 开会可写结束；不能早于开始；待办不保存结束时间 |
| 全天 | 开关，默认否 | `all_day` | 表示整天，不表示“没有期限” |
| 无固定期限 | 只适用于待办 | `is_unscheduled` | 开启后没有执行日期，也不能同时全天 |
| 描述、地点、备注 | 选填 | `description`、`location`、`notes` | 补充内容；不同创建入口展示的输入框不完全相同 |
| 分类 | 默认“其他” | `category` | 出行、工作、社交、生活、健康、其他 |
| 优先级 | 默认“中” | `priority` | 高、中、低，不等于执行期限 |
| 完成状态 | 操作后变化 | `is_completed` | 是否已经做完；完成不会等于删除 |
| 是否重复、重复规则 | 选填 | `is_repeated`、`repeat_rule` | 例如每周同一天，属于原事项的重复属性 |
| 提醒安排 | 选填 | `reminders` | 存提醒设置；不保证手机一定弹闹钟 |
| 高风险标记 | 按入口产生 | `is_high_risk` | 内部风险提示标记，不是另一类事项 |
| 编号、所属账号、创建/修改时间 | 系统自动 | `id`、`user_id`、`created_at`、`updated_at` | 用来识别记录、隔离账号和保留变更时间 |

某个字段存在于保存格式，不意味着每个表单都有同名输入框。例如普通编辑表单有备注，导入接口也可能带描述。完成证明另外保存，可包括完成时间、重新打开时间、说明、金额（内部以分为单位）、币种、账单日期和附件；这些不是创建普通事项时的必填信息。

## 周期事务为什么另有一套？

“每月还信用卡”是一条长期规则；“9 月这一期已经还了”是单独的一期。完成 9 月不会顺带完成 10 月。

周期事务有 **3 种规则模板**，不是再多出三类普通日程：

| 模板 | 必须确定的核心信息 | 其他配置 |
|---|---|---|
| 信用卡 | 名称、账单日、还款日、是否次月还款 | 提前几天提醒、提醒时间、优先级 |
| 手机卡保号 | 名称、间隔天数、上次操作日期 | 运营商、脱敏号码、地区、操作说明、提醒设置 |
| 通用周期 | 名称、起算日期、频率；按频率补充月/日/间隔 | 订阅、保险、证件、会员、房租、水电、车检、自定义模板；操作说明、提醒设置 |

通用频率包括一次性、按月、按年、每隔若干天/月/年；下一期可以按固定日历推进，也可以从实际完成日期起算。字段根据所选频率校验，默认值不等于字段没有意义。

系统还保存：任务编号、所属账号、是否启用、时区、创建和修改时间。提醒默认时间为 12:00、默认时区为 Asia/Shanghai；启用/停用决定是否继续提醒，并不删除过去的记录。

每一期另存：期次编号、属于哪条规则、期次标识、周期开始日、到期日、状态（待处理/完成/过期/取消）、完成时间和完成说明、创建/修改时间。发送记录又单独保存，不能把“发过提醒”理解成“事情做完了”。

## 几个容易混淆的关系

- **日期和时间**：日期决定哪一天；时间进一步限定几点。全天事项的内部零点代表日期，不是约你半夜做事。
- **全天和无期限**：“明天全天”有明确日期；“有空再做”没有。两者不能同时开启。
- **完成和过期**：到了期限但还没做，是过期/逾期；做完才是完成；删除会移除记录，是另一种操作。
- **重复和周期事务**：普通重复事项保存一条事项和重复规则；周期事务保存长期规则和独立期次。需要逐月记录“已还/未还”时，应优先用周期事务。
- **日历里的周期副本**：为了统一展示，周期事务可生成日历记录；手机投影会按来源归并，避免同一期出现两份。

## 现有技术债与最小建议

1. **无期限事项仍有 `start_time`**：旧表要求有时间，系统沿用占位/历史保存时间。它不是执行期限，不能据此显示逾期、安排手机日期或发定时提醒。本次管理页明确标为“历史保存时间（不是执行期限）”。暂不改表、不清洗历史。
2. **空结束时间有多种旧表示**：空字符串、空值，以及过去无期限记录的“结束等于开始”。读取层已经兼容，待办读取时不把它当持续时长。以后写入沿用统一规则，不回写整库。
3. **日期与具体时刻仍共用字符串字段**：全天日期、无时区的本地时刻、带时区的历史时刻不完全一致。新增入口应复用校验；跨时区统一需要单独设计和迁移验证。
4. **普通重复与周期规则并存**：先在界面解释用途；不把两套规则强行合并。尤其不要把普通重复事项的“完成”宣传成已具备每一次独立完成历史。
5. **说明、字段与入口可能漂移**：优先共享校验和补齐真实失败案例，继续使用现有数据层。大规模换模型的收益尚不足以抵消迁移风险。
