# AI Calendar × 荣耀日历 CalDAV 全量测试复盘与下一步改造建议

日期：2026-09-19
报告对象：Astra
报告用途：基于生产全量手动投影结果，评估当前方案，并请求评估下一步业务规则、桥接策略和前端管理改造。
对应版本：`0.25.0-260919.0731`
报告性质：测试复盘与改造建议；本报告不执行代码、数据、服务器或自动化变更。

## 1. 执行摘要

本次已按“全部日历”完成一次生产手动全量投影。桥接的认证、读取、幂等写入、账本、目标集合和失败隔离均得到验证；但当前业务过滤规则仍然排除了已完成项目、周期派生副本和无固定期限待办，并且有 1 条全天语义不明确的待办被保留为例外。

严格结论为：

> **桥接基础链路 PASS WITH LIMITATION；当前业务语义尚未达到“忠实全量同步”，前端也缺少无固定期限待办的完整管理入口。**

本次需要提交 Astra 评估的方向是：

1. 无固定期限待办继续不进入 CalDAV 桥接；
2. 将“挂赵处系统”这类非法的 `all_day + todo + 无明确范围` 数据收口为普通、有开始时间的待办；
3. 后续桥接不再以“已完成”或“周期任务/周期派生副本”为过滤理由，改为忠实投影并通过稳定 UID、来源映射和去重处理一致性；
4. 在前端增加无固定期限待办专门入口，统一管理已完成和未完成项目。

## 4. “挂赵处系统”问题与建议规则

### 4.1 已确认的数据形态

| 字段 | 当前值 | 判断 |
|---|---|---|
| `type` | `todo` | 待办类型正确 |
| `start_time` | `2026-09-20T09:00:00` | 已有明确开始时间 |
| `all_day` | `true` | 与当前有明确时刻的待办语义冲突 |
| `end_time` | 空 | 没有全天范围的结束边界 |
| 完成状态 | 未完成 | 应继续作为可执行项目处理 |
| 桥接结果 | `AMBIGUOUS_ALL_DAY_RANGE` | 当前不能安全生成全天 iCalendar 语义 |

### 4.2 建议收口规则

将以下组合定义为非法：

```text
type = todo
AND all_day = true
AND 没有可解释的有限日期范围
```

对已有的“挂赵处系统”建议执行一次可审计的规范化转换：

```text
type          = todo
is_unscheduled = false
all_day       = false
start_time    = 保留 2026-09-20 09:00
end_time      = null
```

这样它会成为普通的定时待办，可以按现有待办投影规则进入桥接。后续服务器端应在创建、编辑和 AI/导入写入入口统一拒绝或规范化该非法组合，不能继续让同一条数据以“有开始时间但全天范围不明”的状态长期存在。

推荐优先采用“源数据规范化 + 写入校验”，而不是只在桥接层临时猜测。桥接层仍应保留最后一道校验，防止历史脏数据再次进入目标集合。

## 5. 业务处理规则调整建议

### 5.1 无固定期限待办

无固定期限待办继续不进入 CalDAV 桥接。这是有意保留的业务边界，因为它没有稳定的日历执行位置；但它必须在 AI Calendar 前端可完整查看和管理，不能因为完成而从所有正常入口消失。

### 5.2 已完成项目

后续同步不再使用“已完成”作为排除条件。已完成的 event、todo 和符合周期投影规则的项目都应进入同步计划，并保持稳定 UID、幂等更新和可追踪的来源关系。

需要 Astra 进一步确定目标端的完成表达方式：当前荣耀兼容路径将 todo 投影为 `VEVENT`，不能未经验证地把 `STATUS:COMPLETED` 直接套用到 `VEVENT`。应选择经过协议和手机实测的表达方式，至少保证已完成项目仍可见、不会被误当成未完成项目，也不会因下一轮同步被重复创建或撤回。

### 5.3 周期任务与周期派生副本

后续同步不再以“周期任务”或“周期派生副本”作为业务排除理由。建议采用以下规则：

- 周期任务本体和每个可识别的周期实例都进入候选计划；
- 每个周期实例使用稳定的 `cycleId` 或等价来源键生成 UID；
- 周期本体与派生副本不能因为简单过滤而丢失，也不能因重复读取而生成两个相同目标资源；
- 去重应通过来源映射和稳定 UID完成，而不是通过静默排除完成；
- 周期历史、当前周期和已完成周期的展示范围需在预览中逐项列明，不能继续只报告一个总数。

这项规则会扩大同步对象数量，必须同步复核 500 条容量保护、批次删除保护、目标备份和手机端显示承载能力。

### 5.4 仍应保留的边界

以下边界不因本次调整自动放开：

- 未确认的 AI 草稿不得进入正式桥接；
- AI Calendar 仍是唯一数据源，手机继续只读；
- 网络错误、源读取不完整或目标冲突不能触发批量删除；
- 不支持的重复例外、复杂规则和提醒语义必须逐项报告，不能静默伪装成已支持；
- 自动化、手机提醒和双向写入仍需独立授权与验收。

## 6. 前端改进建议：无固定期限待办管理入口

建议新增一个明确的“无固定期限待办”入口，可放在“今日行动中心”顶部或作为独立页面/抽屉。入口的数据条件应是 `is_unscheduled=true`，不能再附带 `is_completed=false` 的隐含过滤。

### 必须支持的能力

| 能力 | 要求 |
|---|---|
| 统一列表 | 已完成和未完成的无固定期限待办全部显示 |
| 状态筛选 | 全部、未完成、已完成 |
| 搜索 | 按标题、备注和说明搜索 |
| 查看详情 | 展示原始待办信息、开始时间、完成状态和完成记录 |
| 状态管理 | 标记完成、设为未完成，操作后仍留在该入口 |
| 编辑 | 修改标题、备注、优先级、开始时间和无固定期限属性 |
| 删除 | 继续使用现有确认和权限边界 |
| 计数 | 分别显示全部、未完成、已完成数量 |
| 移入正常日程 | 用户明确关闭无固定期限后，才允许回到普通日历流 |
| 移动端 | 在现有窄屏和暗色主题下可完整查看、筛选和操作 |

### 建议的用户体验

```text
今日行动中心
├── 无固定期限待办（全部 / 未完成 / 已完成）
├── 今天
├── 明天
├── 即将到期
├── 已经逾期
└── 今天已完成
```

“今天已完成”仍可保留为当天工作回顾；无固定期限待办入口则承担长期历史管理，二者职责不同。全局搜索继续保留，作为跨领域检索入口，而不再承担唯一的历史找回功能。

## 7. 改造量与难度评估

| 改造项 | 预计难度 | 主要影响 |
|---|---|---|
| 非法全天待办规范化与写入校验 | 低至中 | 输入校验、历史数据一次性修正、AI/导入入口回归 |
| 已完成项目纳入桥接 | 中至高 | 投影计划、完成状态表达、同步差异、目标端显示和容量 |
| 周期任务/派生副本忠实投影 | 高 | UID 设计、周期实例生命周期、重复/完成/删除传播、历史范围 |
| 无固定期限待办专门入口 | 中 | action-center 接口或新增查询、前端筛选、详情和移动端交互 |
| 全量回归与手机验收 | 中至高 | 目标备份、预览逐项核对、读者端显示、锁屏/后台/断网观察 |

总体判断：这不是单纯改一个过滤条件。完成项目和周期实例的同步会改变目标数据量与生命周期；无固定期限待办则主要是前端可见性和管理模型问题。可以分阶段实施，不建议一次性绕过预览、容量和手机验收直接开启自动化。

## 8. 建议 Astra 下一步评估和输出

请 Astra 重点确认以下内容：

4. 周期本体、当前周期、历史周期和派生副本的目标端对象边界与 UID 方案；
5. 全量对象扩大后，容量保护、目标备份、删除保护和手机端承载是否需要调整；
6. 无固定期限待办入口采用扩展行动中心还是独立页面，并给出 API、筛选和验收清单；
7. 分阶段实现的预计工作量、风险和放行门槛。

## 9. 最终评价

当前版本已经证明：

- 全部日历范围可以被读取和规划；
- 目标集合可以稳定写入并维护账本；
- 普通可桥接对象的 UID、格式、幂等和失败隔离基本成立；
- 服务器不会因为本次异常自动修改源数据。

当前版本尚未证明：

- 已完成项目可以在荣耀端以正确语义持续可见；
- 周期本体和所有周期实例不会丢失、重复或错误撤回；
- 无固定期限待办可以在前端被长期、统一、可逆地管理；
- 手机端全量显示、修改传播、提醒、断网恢复和后台稳定性已经通过。

因此，本次测试应作为 **PASS WITH LIMITATION** 交给 Astra：基础连接和投影路径可以继续，但下一步应先完成业务规则收口、完成/周期对象语义设计和无固定期限待办入口改造，再进入新的全量预览与手机端验收批次。
