## 权限、存储与复用核对

- 前端为 React 18 / Vite / TDesign / Tailwind，npm 锁文件；Web 与 Electron 共用前端。现有 `useAuth`、`getStoredAuthHeaders`、通知偏好保存后回读服务和 TDesign 控件可以直接复用。
- 四个 sql.js 数据库：`chat.db`、`schedule.db`、`reminder.db`、`activity.db`，由各 Store 初始化并以增量列检查兼容旧数据；测试可通过 `DATA_DIR` 隔离。不打开实际运行数据来推测结构。
- 抽查设置、通知、记事、附件、日报和导出路由，个人 API 使用 `authenticate`，从 JWT 的 userId 派生账户，Store 按 `user_id` 查询；管理接口叠加 `requireAdmin`。附件 GET/DELETE 通过带当前 userId 的元数据查询；上传保留签名/MIME、配额和所有权校验。未发现本次设置改造必须先修复的越权阻塞；这不是全仓库安全认证。
- 日报集成使用哈希保存的独立令牌，日程/邮箱接口只读，但同一令牌也有上传托管媒体和发布日报的能力。媒体公开哈希地址是现有网页/邮件共享约定，不等同于附件私有访问模型。
- Markdown 由现有受限 renderer 和固定 Daily Digest 模板处理，原始 HTML 转义、链接协议过滤；无需为本次设置改造新增 Markdown 或上传依赖。
- 已有 Model、Notification、Mail、Report、Backup、Export、Attachment 等 Service；日历、周期和活动有 Store，避免拆 Router 时再次实现这些逻辑。
- 测试入口是 `tsx --test server/*.test.ts`；含通知回读、用户隔离、QQ 授权码加密、日报发布/媒体、附件/备份等测试。仓库没有独立前端 E2E 配置；本次使用环境自带浏览器能力验证设置，不新增 Phase 3 CI/E2E 框架。
- 部署指导要求本地构建后在生产备份、校验、原子切换；生产运行数据位于部署应用的 `data/`，发布包排除数据、配置与本地指导文件。本次不执行部署。

## 文档与代码冲突

1. 原设置令牌文案称“不能修改数据”，但 `server/index.ts` 的日报媒体上传和发布路由允许同一令牌发布日报。Phase 2 修正文案，明确它可以读取日程/邮箱摘要并发布日报，不能修改日程；不改变权限合同。
2. 原设置及 README 9.7 称只有首次发布才发日报邮件，实际代码和 README 1.1 已支持新内容版本入队、同版本幂等及手动重发。同步纠正文案。
3. README 曾描述在设置中发送测试邮件，但当前设置只有 AI Key 验证和 QQ 未读摘要测试；发送日程邮件入口位于今日页面。按当前实现更正文档，不添加真实发信操作。
